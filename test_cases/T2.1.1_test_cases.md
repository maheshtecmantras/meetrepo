# Test Cases for T2.1.1 - Basic Details Restaurant

Okay, here are two detailed test cases for the provided task, focusing on different aspects of the "Basic Details Restaurant" functionality.

**Test Case 1: Valid Restaurant Details Submission**

*   **Title:** Verify Successful Submission of Valid Restaurant Details
*   **Description:** This test case verifies that a user can successfully submit valid restaurant details including Name, Address, Phone Number, Logo, and Venue Type.
*   **Steps:**

    1.  Navigate to the "Add Restaurant" or "Edit Restaurant Details" page (as applicable based on the flow).
    2.  In the "Restaurant Name" field, enter a valid restaurant name (e.g., "The Cozy Corner Cafe").
    3.  In the "Address" field, enter a valid street address (e.g., "123 Main Street").
    4.  In the "City" field, enter a valid city name (e.g., "Anytown").
    5.  In the "State/Province" field, enter a valid state/province (e.g., "CA" for California).
    6.  In the "Zip/Postal Code" field, enter a valid zip/postal code (e.g., "90210").
    7.  In the "Phone Number" field, enter a valid phone number with appropriate formatting (e.g., "555-123-4567").
    8.  Click the "Upload Logo" button.
    9.  Select a valid image file (e.g., .jpg, .png) that meets the specified size and format requirements (if any).
    10. Select the appropriate Venue Type radio button: e.g. "Bar".
    11. Click the "Save" or "Submit" button.
*   **Expected Result:**

    *   The application should successfully save the restaurant details.
    *   A success message should be displayed to the user (e.g., "Restaurant details saved successfully").
    *   The user should be redirected to a confirmation page or the restaurant details page, where the entered information is accurately displayed.
    *   The uploaded logo should be displayed correctly in the designated area.
    *   The selected Venue Type ("Bar" in this example) should be accurately reflected in the displayed information.
*   **Priority:** High

**Test Case 2:  Invalid Restaurant Details Submission (Phone Number Format)**

*   **Title:** Verify Error Handling for Invalid Phone Number Format
*   **Description:**  This test case verifies that the application correctly handles invalid phone number formats and displays appropriate error messages.
*   **Steps:**

    1.  Navigate to the "Add Restaurant" or "Edit Restaurant Details" page (as applicable based on the flow).
    2.  In the "Restaurant Name" field, enter a valid restaurant name (e.g., "The Spicy Spoon").
    3.  In the "Address" field, enter a valid street address (e.g., "456 Oak Avenue").
    4.  In the "City" field, enter a valid city name (e.g., "Springfield").
    5.  In the "State/Province" field, enter a valid state/province (e.g., "NY" for New York).
    6.  In the "Zip/Postal Code" field, enter a valid zip/postal code (e.g., "10001").
    7.  In the "Phone Number" field, enter an invalid phone number format (e.g., "123").
    8.  Click the "Upload Logo" button.
    9.  Select a valid image file (e.g., .jpg, .png) that meets the specified size and format requirements (if any).
    10. Select the appropriate Venue Type radio button: e.g. "Lounge".
    11. Click the "Save" or "Submit" button.
*   **Expected Result:**

    *   The application should **NOT** save the restaurant details.
    *   An error message should be displayed to the user, specifically indicating that the phone number format is invalid. (e.g., "Invalid phone number format. Please use a valid format such as (XXX) XXX-XXXX or XXX-XXX-XXXX.")
    *   The error message should be clear, concise, and informative.
    *   The focus should remain on the "Phone Number" field or the form itself, allowing the user to correct the input. The other fields should retain their entered values.
*   **Priority:** High

**Explanation of Choices:**

*   **Focus on Critical Aspects:**  These test cases target core functionality (successful submission) and error handling (invalid input).  These are essential for a good user experience.
*   **Detailed Steps:**  The steps are explicit, making it easy for anyone to execute the test case.  They avoid ambiguity.
*   **Clear Expected Results:** The expected results are specific and measurable.  They state exactly what should happen (or not happen) if the test passes or fails.
*   **Priority:** Both test cases are marked "High" because they directly impact the core functionality and usability of the application. If either of these fails, it needs to be addressed immediately.
*   **Phone Number:** I selected phone number as one of the invalid tests because it's common for applications to have specific phone number format requirements.  Testing these requirements is crucial.  Other input types (like Restaurant Name or Address) could also have constraints, but phone numbers are a frequent source of issues.
*   **Venue Type:** Included a venue type check to ensure that selection of the venue type also works properly.

These are just two examples, and more test cases would be required for a comprehensive test suite.  Additional test cases would cover other invalid input scenarios (e.g., invalid email addresses, invalid zip codes, excessively long restaurant names), boundary conditions (e.g., minimum and maximum allowed file sizes for the logo), and negative testing (e.g., attempting to inject malicious code into the input fields).
