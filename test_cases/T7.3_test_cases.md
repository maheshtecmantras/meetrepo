# Test Cases for T7.3 - Support Staff

Okay, here are two detailed test cases for the "Support Staff Access to User Profiles for Support Queries" task, designed from a senior QA engineer's perspective:

**Test Case 1: Successful Support Staff Access to User Profile**

*   **Title:** Verify Support Staff Can Successfully Access User Profile for Support Query

*   **Description:** This test case verifies that a user with the 'Support Staff' role can successfully access a user profile when handling a support query, ensuring they can view relevant information to assist the user effectively.

*   **Steps:**

    1.  **Precondition:** Ensure a user account exists with the 'Support Staff' role.
    2.  **Precondition:** Ensure a separate user account exists representing a "regular user" whose profile will be accessed. Note down this user's User ID.
    3.  Log in to the application using the 'Support Staff' account credentials.
    4.  Navigate to the "Support Dashboard" or equivalent area where support requests are managed.
    5.  Locate a support request/ticket that is associated with the "regular user" noted in step 2. This might involve searching for the user ID or a known identifier of their issue. Alternatively, if the platform supports it, directly input the User ID in a dedicated search or lookup field within the Support Dashboard.
    6.  Click on the link or button labeled "View Profile," "User Details," or similar (wording may vary based on the application) associated with the "regular user" within the support request/ticket.
    7.  Observe the displayed page/modal.

*   **Expected Result:**

    *   The system should successfully redirect the Support Staff user to the "regular user's" profile page or display the profile information within a modal.
    *   The user profile should display relevant information such as:
        *   Username
        *   Email address
        *   Account creation date
        *   Last login date
        *   Subscription status (if applicable)
        *   Order history (if applicable and relevant)
        *   Contact Information (if applicable)
        *   Any other information deemed relevant to support queries (e.g., app version, device type)
    *   The system should NOT display sensitive information that the Support Staff user is not authorized to view, such as:
        *   Passwords (even masked ones)
        *   Full credit card numbers
        *   Security questions/answers
    *   No error messages or unexpected behavior should occur during the profile access process.
    *   The profile page should load within an acceptable timeframe (e.g., less than 3 seconds).

*   **Priority:** High

**Test Case 2: Unauthorized Access Attempt to User Profile**

*   **Title:** Verify Unauthorized User Cannot Access User Profiles

*   **Description:** This test case verifies that a user who does not have the 'Support Staff' role (e.g., a standard user or a guest) cannot access user profiles through any means, ensuring data privacy and security.

*   **Steps:**

    1.  **Precondition:** Ensure a user account exists with a role *other than* 'Support Staff' (e.g., "Regular User," "Guest," etc.). Note down this user's User ID.
    2.  **Precondition:** Ensure a separate user account exists representing a user to protect. Note down this user's User ID.
    3.  Log in to the application using the user account credentials from step 1 (the non-Support Staff account).
    4.  Attempt to access a user profile using one or more of the following methods:
        *   **Direct URL Manipulation:** Attempt to directly access a user profile by manually constructing a URL, such as `/users/{UserID}` or `/profile/{UserID}`, replacing `{UserID}` with the User ID of the other user (from precondition 2). Try variations of the URL with different profile endpoint naming conventions.
        *   **Support Dashboard Simulation:** If possible, try to mimic the steps a Support Staff user would take to find the user profile, even without the correct interface.  For example, if you know the URL structure *would* include a userID try to insert it directly to navigate there.
        *   **API Attempt (if applicable):** If the application exposes an API, attempt to access the user profile data via the API endpoint (e.g., `GET /api/users/{UserID}`) using the non-Support Staff user's authentication token or credentials.
        *   **Search Feature Exploitation:** If a search function exists, try searching for the user's username or email address and attempt to access the profile from the search results (if any are returned).
        *   **Exploit any potential links:** Review if user is associated with content such as a forum post, comment, or other profile related link. If such content exists, attempt to access the user profile via links associated with that content.
    5.  Observe the system's response.

*   **Expected Result:**

    *   For all attempts to access the user profile:
        *   The system should deny access to the user profile.
        *   An appropriate error message should be displayed, such as "Unauthorized," "Access Denied," "You do not have permission to view this page," or similar.
        *   The system should redirect the user to an appropriate page (e.g., the user's own profile, the home page, or an error page).
        *   If attempting to access via the API, the API should return an HTTP 401 (Unauthorized) or 403 (Forbidden) status code, along with an appropriate error message in the response body.
    *   The system should *not* leak any user profile information to the unauthorized user.
    *   The actions should be logged for auditing purposes.

*   **Priority:** High
