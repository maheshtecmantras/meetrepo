# Test Cases for T4.2 - Other Notifications

Okay, here are two detailed test cases based on the provided task "Other Notifications: Implement Reminder Notifications, Capacity / Sell-Out Alerts."  I've aimed for clarity and focus on critical aspects of these notification types.

**Test Case 1: Reminder Notifications - Event Attendance Reminder**

*   **Title:** Verify Reminder Notification Delivery and Content for Event Attendance

*   **Description:** This test case validates that reminder notifications are delivered as scheduled before an event, and that the notification contains accurate and relevant event information. It ensures users receive timely reminders and can act upon them (e.g., confirm attendance, view details).

*   **Steps:**

    1.  **Precondition:** A user account exists and is logged in.
    2.  **Precondition:** A future event (e.g., a webinar, workshop, class) has been created with a specified start date and time (at least 24 hours in the future).
    3.  **Precondition:** The user has registered/signed up/reserved a spot for the event.
    4.  **Precondition:** Reminder notifications for this event type are enabled in the user's notification settings (if configurable).
    5.  **Action:** Note the current system time.
    6.  **Action:** Wait until the scheduled reminder notification time.  Assume a reminder is configured to send 24 hours before the event start time. (Alternatively, manipulate the system time if possible in a testing environment to expedite the test).
    7.  **Action:** Check for the arrival of the reminder notification via the expected delivery method (e.g., in-app notification, push notification, email).
    8.  **Action:** Inspect the content of the notification.
    9. **Action:** Click/Tap on the notification.

*   **Expected Result:**

    1.  A reminder notification is delivered via the expected method (e.g., in-app, push, email) within +/- 5 minutes of the scheduled time (allowing for reasonable system latency).
    2.  The notification content contains the following information:
        *   The name of the event.
        *   The event start date and time in the user's local time zone.
        *   A clear message indicating that it is a reminder for the event (e.g., "Reminder: Your upcoming [Event Name]").
        *   A call to action (CTA) such as: "View Details", "Confirm Attendance", "Add to Calendar", or "Manage Registration."
    3.  Clicking/Tapping the notification redirects the user to the event details page within the application.
    4.  Verify that the "Add to Calendar" function works as expected, adding the event to the user's calendar application (if this functionality exists).

*   **Priority:** High - Critical for user engagement and ensuring attendance.

**Test Case 2: Capacity/Sell-Out Alert - Event Full Notification**

*   **Title:** Verify "Event Full" Notification for Over-Capacity Registrations

*   **Description:**  This test case validates that when an event reaches its maximum capacity, subsequent registration attempts trigger an appropriate "Event Full" notification, preventing overbooking and informing users.

*   **Steps:**

    1.  **Precondition:** A user account exists and is logged in.
    2.  **Precondition:** An event (e.g., a workshop, class) has been created with a defined maximum capacity (e.g., 10 slots).
    3.  **Precondition:** The event's capacity is currently full (10/10 slots are occupied by other users). Simulate this by creating/registering enough "dummy" users.
    4.  **Action:** A new user attempts to register/sign up for the event via the normal registration process.
    5.  **Action:** Observe the behavior of the application.

*   **Expected Result:**

    1.  The user receives an immediate notification indicating that the event is full/sold out.
    2.  The notification provides a clear and informative message (e.g., "This event is currently full.  Please check back later for cancellations or openings.", or "Registration is closed as this event has reached its maximum capacity.").
    3.  The notification prevents the user from completing the registration process.
    4.  The notification prevents the user from being added to a waitlist (if this functionality is not available).  If a waitlist *is* available, the notification should clearly offer the user the option to join the waitlist.
    5.  If a waitlist is offered:
        *   Joining the waitlist should trigger a confirmation notification (e.g., "You have been added to the waitlist for [Event Name].  We will notify you if a spot becomes available.").
        *   The user's profile should correctly reflect their status on the waitlist.
    6.  If the application supports it, verify that the number of people registered for the event *cannot* exceed the defined maximum capacity.  Attempt to circumvent the UI and directly manipulate the database (if possible in a test environment) to verify that the system prevents exceeding the capacity at a data level.

*   **Priority:** High - Critical for preventing overbooking, managing user expectations, and maintaining system integrity.
