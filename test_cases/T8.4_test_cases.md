# Test Cases for T8.4 - Security & Compliance

Okay, here are two detailed test cases for the provided task "Security & Compliance" with a focus on Data Encryption and GDPR Compliance, as these are the most immediately testable aspects of the task.  I'll prioritize them assuming data security and privacy are paramount.  I'll focus on functional testing as a QA engineer. Note that this would be part of a larger security testing strategy that would also include penetration testing, vulnerability scanning, etc.

**Test Case 1: Data Encryption - Data at Rest**

*   **Title:** Verify Encryption of Sensitive Data at Rest

*   **Description:** This test case verifies that sensitive data, as defined by GDPR (e.g., personal data, PII), is encrypted at rest within the database and/or file storage system. This ensures that unauthorized access to the underlying storage medium does not result in data compromise.

*   **Steps:**

    1.  **Identify Sensitive Data Fields:**  Review the data model and GDPR documentation to identify fields containing sensitive personal data (e.g., name, address, email, phone number, social security number/national ID if applicable, date of birth, payment information).  Document these fields (e.g., `users.email`, `orders.billing_address`).
    2.  **Locate Data Storage:** Identify the database(s) and/or file storage system(s) where the identified sensitive data is stored (e.g., PostgreSQL database, AWS S3 bucket).
    3.  **Access Database/Storage Directly (Unauthorized):** Using an account *without* the application's access controls, but with direct database/storage access (e.g., a database administrator account), connect to the database/storage system.  *Note: This step requires controlled access and is typically done in a test/staging environment only to avoid impacting production data.*
    4.  **Query/Retrieve Encrypted Data:**
        *   **Database:** Execute SQL queries to retrieve data from the identified sensitive data fields (e.g., `SELECT email FROM users WHERE id = 123;`).
        *   **File Storage:** Retrieve files known to contain sensitive data.
    5.  **Analyze Retrieved Data:**  Examine the retrieved data to verify its encryption status.  Look for characteristics such as:
        *   **Unreadable format:**  The data should appear as a seemingly random string of characters (ciphertext) rather than the original plaintext value.  Examples: `gAAAAABkN3gJ...`, `AES:someRandomSalt:encryptedData`.
        *   **Consistent encryption:**  The same plaintext value, when encrypted multiple times, should produce different ciphertext results if a proper encryption scheme with salting/initialization vectors is used. This tests for secure salting/IV implementation.
        *   **Absence of plaintext values:** Ensure the raw data isn't stored unencrypted alongside metadata.
    6. **Repeat the steps on other sensitive data fields.**

*   **Expected Result:**

    *   All identified sensitive data fields at rest must be stored in an encrypted format.
    *   The encrypted data should be unreadable without proper decryption keys and access.
    *   Multiple retrievals of the same plaintext value should result in different ciphertext, if salting/initialization vectors are used.
    *   No sensitive information should be directly readable in plain text.

*   **Priority:** HIGH (Critical for security and compliance)

**Test Case 2: GDPR Compliance - Data Subject Access Request (DSAR)**

*   **Title:** Verify Data Subject Access Request (DSAR) Fulfillment

*   **Description:** This test case verifies that the system can properly handle a Data Subject Access Request (DSAR) as required by GDPR. Specifically, it tests the ability to retrieve and provide all personal data related to a specific user in a readily understandable format.

*   **Steps:**

    1.  **Create a User Account:** Create a new user account with realistic personal data, including:
        *   Name
        *   Address
        *   Email Address
        *   Phone Number
        *   Other relevant information that the application collects (e.g., preferences, purchase history, usage data).
    2.  **Interact with the Application:**  Use the newly created account to interact with the application, generating data across various features (e.g., place orders, submit forms, update profile settings). This is important to ensure data is captured in different parts of the system.
    3.  **Submit a DSAR:**  As the user, submit a formal Data Subject Access Request (DSAR) through the application's designated mechanism (e.g., a form on the website, an email to a designated address).
    4.  **Monitor DSAR Processing:**  Monitor the system's processing of the DSAR. Ideally, the system should provide updates on the status of the request (e.g., "Received," "Processing," "Completed").
    5.  **Receive DSAR Response:**  Receive the response to the DSAR, which should contain all personal data related to the user.
    6.  **Verify Data Accuracy and Completeness:**  Thoroughly review the received data to ensure:
        *   **Accuracy:** The data matches the information provided during account creation and subsequent interactions.
        *   **Completeness:** All relevant personal data is included in the response, including data from all relevant parts of the system. This includes data that may not be immediately obvious from the user interface (e.g., IP addresses, log entries, server-side tracking data, etc., if applicable and considered personal data under GDPR).
        *   **Format:** The data is presented in a clear, understandable, and portable format (e.g., JSON, CSV, or a well-structured PDF).  The format should allow the user to easily understand the information and potentially transfer it to another service.
        *   **Timeliness:** The response was provided within the timeframe specified by GDPR (typically 30 days, but check local regulations).  Document the date the DSAR was submitted and the date the response was received.
    7. **Repeat steps for different users with varying degrees of application interaction.**

*   **Expected Result:**

    *   The user receives a complete and accurate copy of their personal data within the GDPR-mandated timeframe.
    *   The data is presented in a readily understandable and portable format.
    *   All personal data across the application, not just data visible in the user interface, is included in the response.
    *   The DSAR process functions correctly, providing appropriate status updates to the user.

*   **Priority:** HIGH (Critical for legal compliance and user trust)

**Important Considerations and Next Steps:**

*   **Scope:** These test cases cover only two aspects of the overall task.  You'll need to develop additional test cases for Audit Logs, Data Retention, and other relevant security and compliance requirements.
*   **Environment:** Testing should be performed in a dedicated test/staging environment that mirrors the production environment as closely as possible.  Never test security features directly in production without proper safeguards.
*   **Collaboration:** Work closely with developers, security engineers, and legal counsel to ensure a comprehensive and effective testing strategy.
*   **Documentation:**  Maintain detailed records of all test results, including any failures or discrepancies.  This documentation is essential for audits and compliance reporting.
*   **Automation:** Consider automating some of these test cases, especially the DSAR fulfillment process, to ensure ongoing compliance.
*   **Security Expertise:** Engage security experts to perform penetration testing and vulnerability assessments to identify potential weaknesses in the system's security.
*   **GDPR Regulations:** Keep up to date with the latest GDPR regulations and guidelines, as they can change over time.

These test cases provide a starting point for verifying the security and compliance aspects of your application. Remember to tailor them to your specific requirements and context. Good luck!
