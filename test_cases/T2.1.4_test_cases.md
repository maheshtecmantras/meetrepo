# Test Cases for T2.1.4 - Venue Status Management Restaurant

Okay, here are two detailed test cases based on the provided task "Venue Status Management Restaurant: Manage Signed/Not Signed status". These test cases cover both positive and negative scenarios, ensuring robustness of the functionality.

**Test Case 1: Verify Ability to Successfully Mark a Venue as "Signed"**

*   **Title:** Verify Venue Status can be Updated to "Signed"

*   **Description:** This test case verifies that a user with appropriate permissions can successfully update a restaurant's venue status from "Not Signed" to "Signed" within the system. This validates the core functionality of changing the venue's agreement status.

*   **Steps:**

    1.  **Precondition:** A restaurant venue exists in the system with its initial status set to "Not Signed". User is logged in with sufficient permissions (e.g., "Venue Manager", "Administrator").
    2.  Navigate to the "Venue Management" section in the application.
    3.  Locate the specific restaurant venue to be updated. (Consider adding search or filtering criteria for large lists)
    4.  Identify the "Status" field or control associated with the venue.  (e.g., a dropdown menu, a toggle switch, or a clickable button labeled "Mark as Signed").
    5.  Select the "Signed" option from the status control.
    6.  If a confirmation prompt appears (e.g., "Are you sure you want to mark this venue as Signed?"), confirm the action.
    7.  Observe the application for visual feedback indicating successful status update.  (e.g., a success message, an updated status display on the venue's details page).
    8.  Refresh the Venue Management page or navigate away and back to the venue's details page.

*   **Expected Result:**

    1.  The venue's status is successfully updated to "Signed".
    2.  A visual confirmation (e.g., a success message like "Venue status updated successfully") is displayed to the user upon saving.
    3.  When the venue details page is reloaded, the status remains as "Signed".
    4.  An audit log entry is created, recording the user who made the change, the date and time of the change, and the previous and new statuses. (This is ideal, but may depend on system capabilities).

*   **Priority:** High

**Test Case 2: Verify User Without Permissions Cannot Change Venue Status**

*   **Title:** Verify Unauthorized User Cannot Update Venue Status

*   **Description:** This test case verifies that a user without the required permissions cannot change the venue status of a restaurant (either "Signed" to "Not Signed" or "Not Signed" to "Signed"). This ensures proper access control and data integrity.

*   **Steps:**

    1.  **Precondition:** A restaurant venue exists in the system. User is logged in with *insufficient* permissions (e.g., "Guest", "Basic User" without venue management rights).
    2.  Navigate to the "Venue Management" section or the specific restaurant venue's detail page.
    3.  Locate the "Status" field or control associated with the venue (e.g., a dropdown menu, a toggle switch, or a clickable button labeled "Mark as Signed").
    4.  Attempt to modify the "Status" field.  (e.g., try to select a different option from the dropdown, try to toggle the switch, try to click the "Mark as Signed" button).
    5.  Observe the application's behavior.

*   **Expected Result:**

    1.  The "Status" field/control is either:
        *   Disabled (greyed out) and un-editable, *or*
        *   Present but attempting to modify it results in an error message indicating insufficient permissions (e.g., "You do not have permission to perform this action").
    2.  The venue's status remains unchanged.
    3.  No audit log entry is created (if audit logging is implemented).

*   **Priority:** High
